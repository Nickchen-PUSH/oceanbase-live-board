# 出分预测与耗时模型

> 代码：`src/shared/stats.ts`（数值工具）、`src/shared/timing.ts`（耗时清洗模型）、`src/shared/predict.ts`（出分预测 + 回测）。
> 回测：`bun scripts/backtest.ts`（加 `--md` 输出本文表格；`VARIANTS='{"名字":{...EngineCfg}}'` 做消融）。
> 全部为纯 TypeScript、无依赖，浏览器 / Cloudflare Worker / Bun 通用；时间一律毫秒时间戳，钟点一律北京时间。

## 1. 数据从哪来、能说明什么

赛道榜每行是「该队最优那次提交」：`bestSubmit`（gmtCreate）= 提测时刻，`updated`（gmtModified）= 出分时刻。两份快照对比证实二者**当且仅当分数提升时**一起变化，所以

- `updated − bestSubmit` = 这次提交真实的端到端耗时（排队 + 评测）；
- 没提分的提交不可见（**幸存者偏差**），越早的日子剩下的样本越少；
- 我们看不到「此刻有多少作业在排队」，只能从「最近出分的作业等了多久」推断。

## 2. 耗时模型（timing.ts）

与旧版 `public/app.js` 同口径移植，并修掉了以下问题：

| 问题 | 处理 |
|---|---|
| 「极端异常」把「扣暂停后变 0」和真异常混在一起 | `cleanup.outlierN`（> 围栏）与 `cleanup.zeroedN`（扣暂停后 ≤0）分开计数 |
| 「最近窗口」相对最后一次**提交** | `recent` 相对 **now**：近 30 分钟出分，不足 5 条退回最近 20 条；`recent.stale / ageSec` 标出样本过旧 |
| 停摆不可见 | 新增 `idleSec`（距最近出分）、`stallSec`（= max(60 分钟, 10 × 出分间隔中位数)）、`stalled` |
| inflight 计数 O(n²) | 改为两次二分 O(n log n)；650 行 × 11 赛道约 13ms |

- **暂停识别**：相邻出分间隔 ≥ max(60 分钟, 10 × 间隔中位数) 视为暂停窗口；暂停总时长超过跨度 60% 视为「本来就稀疏」不识别。只保留真正覆盖到某条作业等待期的窗口，并从这些作业的耗时中扣除。
- **异常围栏**：fence = max(P99, 10 × 中位数, 60 秒)。
- **评测时长**：measured（空闲时提交、无暂停干扰的作业 ≥ 20 条取中位数）→ inferred（出分节拍 × 2.5，封顶全体中位数 × 0.9）→ fallback（min(P20, 300 秒)）。
- **滚动窗口 series**：窗口 w = clamp(round(n/10), 5, 80)，步长 ⌊w/4⌋。

## 3. 出分预测（predict.ts）

### 3.1 旧算法（baseline，`predictLegacy` 原样保留）

队头推进速率 r = Δ(队头提交时刻) / Δ(时钟)，取 6/24/72h 第一个可用窗口；预计出分 = now + (提交时刻 − 队头位置)/r + 评测时长；中位耗时 ≤ 15 分钟走「快赛道」；量不出 r 走「批量窗口」。回测发现它有三个系统性问题：

1. **重复计入评测时间**：队头 = 刚出分作业的提交时刻，它已经包含了评测耗时，再加 judge 等于算两遍 ⇒ PowerContext 恒定偏晚 +17 分钟、seekdb 性能优化偏晚 +9.6 分钟（覆盖率 2% / 27%）。
2. **两端点相减**的速率对单个异常点极敏感；回填期（r 达 10×）外推会严重偏早。
3. 夜间不评测的赛道（Dify、MiniMax）被当成「排队」外推，偏早十几小时；量不出速率的快赛道被误判为批量（判断顺序错）。

### 3.2 新算法

**(1) 工作时钟。** 从历史学出「评测机不干活的北京时间小时」：某小时 h 在 ≥2 个不同日期里都有作业**整小时在等**，却在所有日期里从没在 h 点出过分 ⇒ h 为休息钟点。夜里没人提交的空闲时段没有在等的作业，不会被误判。随后所有耗时都在「只计工作小时」的时钟下计算（全天工作的赛道等同普通时钟）。当前数据学出：Dify 1–8 点、Qoder 5–6 点、AMD 21–22 点、MiniMax 17–20 点与 23–8 点。

**(2) 点估计 = 近期滞后水平。** L̂ = 最近 5 条出分（工作时钟）耗时的中位数，下限为窗口（最近 30 条且 12 小时内）最小耗时。直观含义：「刚出分的作业等了多久，你大概也要等多久」。它天然包含排队 + 评测，不会重复计算；中位数抗单点异常。试过 Theil–Sen 趋势外推（阻尼 0.5/1.0）与 3/7 条水平，回测均无稳定改善，按「简单优先」舍弃。

**(3) 区间 = 经验残差校准。** 对最近 50 条已出分样本，回放「它刚提交时」本模型的点估计 ĥⱼ，得到比值 ρⱼ = 实际/ĥⱼ 的经验分布；把 ρ^1.3（对数尺度放宽 1.3 倍）乘到当前 L̂ 上，取 5%/95% 分位作为区间。只用 10%/90% 分位、不放宽时正常时段实际命中率只有 58%（近期节奏会漂移），放宽后提到 74%，这是按回测**校准**出的参数。

**(4) 条件化。** 若已经等了 e，只保留 ρL̂ > e 的情形重新取分位；若 L̂ 已被等过，点估计改为条件中位数。若剩下的情形不足 1/6 ⇒ `overdue`（随时可能出分）。

**(5) 类型判定（顺序即优先级）**：

| kind | 条件 | 说明 |
|---|---|---|
| `none` | 可见出分 < 3 条 | 无法预测 |
| `stalled` | 此刻是工作钟点，且距最近出分 > max(1 小时, 10 × 近期出分间隔, 2 × L̂) | 仍给出「恢复后按此前节奏」的 eta，置信度 low |
| `overdue` | 条件分布几乎为空 | eta = 此刻之后不久 |
| `batch` | 预计等待跨越休息钟点 ≥ 30 分钟 | 文案说明休息钟点 |
| `fast` | L̂ ≤ 3 分钟 | 文案用「X 秒内出分」 |
| `queue` | 其余 | |

**(6) 置信度**：优先看该赛道近 24h 滚动回测（`Prediction.accuracy`）：相对误差 = 中位绝对误差 / max(近期耗时中位数, 2 分钟)，≤0.25 high、≤0.6 medium、否则 low；区间命中率 < 60% 再降一级；stalled 或样本 < 10 一律 low，overdue 至多 medium。回测样本不足时退回看区间相对宽度。

### 3.3 其它字段

- `frontMs`：队头此刻推进到的提交时刻 = 工作时钟下 now − L̂；`backlogSec = now − frontMs`。
- `rate`：窗口内「提交时刻 ~ 出分时刻」的 Theil–Sen 斜率（稳健回归，代替两端点相减）；`rateLabel`：≥2.5 回填中、>1.25 积压被消化、≥0.8 饱和、否则积压在增长。
- `medTurnaroundSec / p90TurnaroundSec`：窗口内、**清洗后**（扣暂停、去异常）的耗时。
- `backtestTrack(rows, now)`：近 24h 内提交的作业，以提交时刻为起点回放预测（最多 80 例，等距抽样），650 行单赛道约 1ms。

## 4. 回测

两种验证，指标：**中位绝对误差 / P80 绝对误差 / 80% 区间实际覆盖率 / 偏差**（误差中位数，正 = 预测偏晚）。

- **① 跨快照真·未来**：只用 `snapshot-1029.json`（2026-10-29 17:26 北京）里的信息，在该时刻预测，与约 23 小时后 `snapshot-live.json` 中的真实出分对比。A = 当时已提交未出分；B = 之后才提交（预测时刻仍是 10-29 17:26，属于「提前很久预测」）。
- **② 滚动起点**：live 快照近 72h 内提交的每条作业，在提交后 0 / 15 分钟 / 1 小时 / 4 小时（尚未出分时）各预测一次，信息集 = 当时已出分的样本。RN = 排除等待期与评测暂停重叠 ≥10 分钟的作业（正常时段）。
- 列「新·无工作时钟」「新·10/90 分位未放宽」是消融，用来说明各组件的贡献。

### 4.1 结论

- **正常时段（RN，4283 例）**：中位绝对误差 12 分钟 → **3.5 分钟**，区间覆盖率 37% → **74%**，几乎无偏（+1 秒）。最大的改善来自修掉「重复计入评测」：PowerContext 17 分钟 → 2.1 分钟、seekdb 性能优化 11 分钟 → 2.8 分钟；秒级赛道持平（4~6 秒），覆盖率从 ~70% 升到 ~90%。
- **全部（R，5138 例，含停摆）**：中位 18 分钟 → **6.7 分钟**，P80 6.3 小时 → 3.9 小时，覆盖 31% → 66%。
- **工作时钟**：Dify 偏差 −8.4 小时（旧）/ −7.1 小时（新·无工作时钟）→ **−51 分钟**，中位误差 9.7 → 4.6 小时；AMD 中位 2.8 → 1.9 小时。
- **跨快照 A（194 例）**：中位 17.3 → 8.4 小时、覆盖 6% → 80%；主要是 MiniMax（4 → 148 行的批量赛道），旧算法偏早 18 小时，新算法偏晚 11.5 小时但区间覆盖。**B** 中位 15 → 3.6 分钟、P80 50 → 17 分钟；覆盖率低于旧版（67% vs 75%），因为旧版在 seekdb 性能优化 / PowerContext 上的区间是靠整体偏晚 +20~40 分钟「碰巧罩住」的。

### 4.2 已知局限

1. **停摆不可预测**：高德、Qoder 的历史停摆（5~16 小时）在发生前没有任何信号，R 表里这两条赛道 P80 仍是小时级。模型只能在停摆**发生后**识别为 `stalled` 并明确告知「恢复时间无法预估」。
2. **Dify / AMD / MiniMax 仍然很难**：Dify 晚间是否评测每天不同（休息钟点只学出 1–8 点），夜间提交的作业仍会被低估；AMD 是长 FIFO 队列，耗时随提交密度剧烈变化（3~9.5 小时）；MiniMax 只有一两天数据。这三条赛道的置信度通常是 medium/low，前端应如实显示。
3. **幸存者偏差**：只看得到提分的提交，排队长度被低估；但这对「提交后多久出分」影响不大（同一队列里提分与不提分的作业等待相同）。
4. **工作时钟用全部历史学习**：`backtestTrack` 与滚动回测里休息钟点是用整份数据学的（轻微前视）；跨快照验证没有这个问题。
5. **快赛道覆盖率偏高（~90%+）、慢赛道偏低**：区间放宽系数是全局统一的，没有按赛道单独调，以免对两份快照过拟合。
